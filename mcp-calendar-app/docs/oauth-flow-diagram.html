🔐 MCP OAuth 2.1 Authorization Flow

How MCP Clients authenticate with OAuth-protected MCP Servers

💻
MCP Client
VS Code, Claude Desktop, or any MCP-compatible client
🖥️
MCP Server
OAuth-protected resource server (Calendar, Tools, etc.)
🔑
Authorization Server
Keycloak, Auth0, Okta, or any OAuth 2.1 provider
1
Initial Handshake
Client MCP Server

The client attempts to connect without credentials. The server responds with 401 Unauthorized and includes a pointer to the Protected Resource Metadata (PRM) document.

MCP Client
→ GET /sse (no token) →
MCP Server
MCP Server
→ 401 + WWW-Authenticate header →
MCP Client
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer realm="mcp",
  resource_metadata="https://server/.well-known/oauth-protected-resource"
2
Protected Resource Metadata (PRM) Discovery
Client MCP Server

The client fetches the PRM document (RFC 9728) to learn about OAuth requirements: which authorization server to use, required scopes, and how to send tokens.

MCP Client
→ GET /.well-known/oauth-protected-resource →
MCP Server
// PRM Document (RFC 9728)
{
  "resource": "http://localhost:3000",
  "authorization_servers": ["http://localhost:8080/realms/master"],
  "scopes_supported": ["mcp:tools"],
  "bearer_methods_supported": ["header"]
}
3
Authorization Server Discovery
Client Auth Server

The client fetches the OIDC Discovery document from the authorization server to learn its endpoints: authorization, token, introspection, and registration.

MCP Client
→ GET /.well-known/openid-configuration →
Keycloak
// OIDC Discovery Document
{
  "issuer": "http://localhost:8080/realms/master",
  "authorization_endpoint": ".../.../auth",
  "token_endpoint": ".../.../token",
  "introspection_endpoint": ".../.../introspect",
  "registration_endpoint": ".../.../register"
}
4
Client Registration
Client Auth Server

The client must be registered with the authorization server. This can be done via: pre-registration (credentials configured ahead of time) or Dynamic Client Registration (DCR) at runtime.

MCP Client
→ POST /register (DCR) or use pre-registered credentials →
Keycloak
// Pre-registered or DCR response
{
  "client_id": "mcp-client",
  "client_secret": "zrqR06T0NBTct1ZP...",
  "redirect_uris": ["http://localhost:3000/callback"],
  "grant_types": ["authorization_code", "refresh_token"]
}
5
User Authorization
Client Auth Server

The client opens a browser to the authorization endpoint. The user logs in, grants permissions, and the auth server returns an authorization code. The client exchanges this code (with PKCE proof) for an access token.

MCP Client
→ 🌐 Browser → /authorize →
Keycloak
Keycloak
→ 👤 User logs in → auth_code →
MCP Client
MCP Client
→ POST /token (code + PKCE) →
Keycloak
// Token Response
{
  "access_token": "eyJhbGciOiJSUzI1NiIs...",
  "refresh_token": "def502...",
  "token_type": "Bearer",
  "expires_in": 3600,
  "scope": "mcp:tools"
}
6
Making Authenticated Requests
Client MCP Server Auth Server

The client includes the access token in the Authorization header. The MCP server validates the token via introspection (RFC 7662) with the auth server, then processes the request if valid.

MCP Client
→ GET /sse + Authorization: Bearer token →
MCP Server
MCP Server
→ POST /introspect (validate token) →
Keycloak
MCP Server
→ ✅ SSE Stream (tools, resources) →
MCP Client
// Authenticated Request
GET /sse HTTP/1.1
Host: localhost:3000
Authorization: Bearer eyJhbGciOiJSUzI1NiIs...
Accept: text/event-stream
